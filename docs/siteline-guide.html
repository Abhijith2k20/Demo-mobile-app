Siteline in five minutes

Siteline is a work chat app for companies with people out in the field: interior designers, event crews, builders. It replaces the WhatsApp groups they use today, and lets the company's project-management app ask people for updates without anyone typing.

Chat, like Slack or WhatsApp

Each company gets its own workspace: projects with channels, company channels, direct messages, threads, photos, voice notes and files.

A bot that asks for updates

The company's project-management (PM) app sends a person a card, for example "How far is the false ceiling?" with a one-tap 25% / 50% / 75% / Done. The answer goes straight back to the PM app.

Many companies, kept apart

Every company is a separate "tenant". Nothing from one company is ever visible to another. One person can belong to several companies and switch between them.

The one idea to remember

The PM app (where the company plans projects and tasks) and Siteline (where people talk) have separate jobs:

PM app decideswhat to ask, whom, and when
→
Siteline deliversshows the card on the person's phone, with a push
→
Person taps an answereven with no signal on site
→
Siteline sends it backto the PM app, signed, retried for 24 hours
Siteline knows nothing about tasks. It keeps no copy of the PM app's projects or tasks and has no rules about them. The PM app can't see Siteline's channels or messages either. This works like the WhatsApp Business API: the business system decides, the messaging app delivers.

People and roles

Every person in a company has one role. The role decides what they can see and do. The server checks it on every request, and the app only shows what the server allows.

Rules that apply to everyone

  • Edit your own message within 15 minutes; delete it within 1 hour.
  • DMs are private to the two people. Owners and admins never see other people's DMs.
  • #general can't be renamed, made private, deleted or left.
  • Archived projects are read-only.
  • Adding someone to a project puts them in all its public channels. Private channels have only the people picked.
  • Deactivating someone ends their access to that company only. Their messages stay under their name.
One person, several companies. A subcontractor can work for two firms. They sign in once, then pick or switch companies. Each company sees only its own part.

    Four rules the whole design follows

    1. Thin client

    Every rule, permission and calculation lives on the server (rules.py, views.py). The app shows what the server returns, such as canEdit, and never works results out itself.

    2. Company from the session, never the request

    The server reads the company from your sign-in. A companyId sent in a request is ignored. Another company's ids answer "not found".

    3. Timed work is a job

    Emails, pushes and webhooks are rows in a jobs table, saved in the same transaction as the change. A crash never loses one, and they retry.

    4. Events say "this changed", not what

    Live updates carry ids only. The app re-fetches from the server, so it never shows data it isn't allowed to see.

    How it's built

    Code structure

    Two top-level folders: frontend/ (the phone app) and backend/ (the server). Open the folders to see what each part is for.

    Layering rules (checked by tests)

    In the app
    • Files in app/ are routes only: read the URL, render a screen from src/features/<area>/screens/.
    • Screens never call the API directly: reads go through feature hooks, writes through the feature's api.ts.
    • Features never import each other in a loop, and features/shared imports no feature (boundaries.test.ts).
    • Only src/lib/api/transport.ts knows the server address.
    • Colours, spacing and type come only from src/theme. Every text is t('key', 'English').
    On the server
    • Routers translate HTTP only. Business actions live in services/.
    • Permissions and rules live only in rules.py; who can see what lives in access.py.
    • What a record looks like to a viewer is built in views.py.
    • Only main.py imports routers (checked by a test).
    • Schema changes are new numbered SQL files; a migration that ran is never edited.

    How it's built

    Data

    Everything lives in one Postgres database. Most tables belong to a company and are locked to it by row-level security. A few are "global": they describe people, companies and sign-in across companies.

    How companies are kept apart

    From the session

    Each request's company comes from the person's sign-in session.

    Set on the transaction

    Every database transaction starts by setting app.company_id.

    Enforced by Postgres

    Row-level security policies return only that company's rows. A forgotten filter returns nothing, not someone else's data.

    One thing to watch: global tables (invites, integrations, jobs, audit log) have no row-level security by design, so queries on them filter by company by hand. New queries on them need the same care.

    Message types

    textimagevoicefilecardsystem

    An unknown type (for example from a newer app version) shows "Update the app to see this message".

    How it's built

    Security

    How Siteline protects people's data. All of these are built and covered by automated tests, and an audit of 20 common mistakes fixed every finding. They have not yet had an outside security review.

    What is and isn't secret

    Secret, server only

    Kept in backend/.env locally and the Render dashboard when live. Never in the app or in git.

    • SITELINE_SECRET: the master key (signs codes, sessions, file links, encrypts PM keys)
    • SITELINE_PLATFORM_KEY, DATABASE_URL
    • R2, Resend and Expo access keys
    Public, fine in the app

    Built into the app, so anyone can read them. That's expected, because safety comes from the server's checks.

    • EXPO_PUBLIC_API_URL: the API's address, set in the Expo dashboard
    • App ids (app.siteline.mobile) and the link scheme

    Server

    Locally: backend/.env (copy .env.example, which lists and explains every setting). Live: the Render dashboard, listed in render.yaml.

python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env
.venv/bin/uvicorn app.main:app \
  --host 0.0.0.0 --port 8000 --env-file .env

    Demo companies are seeded; every code is 123456. Platform panel: localhost:8000/platform (admin@siteline.app).

    2 · App
    cd frontend
npm install
npx expo start

    Push notifications need a development build (npx eas-cli@latest build --profile development). Expo Go for SDK 58 works for a quick look.

    Checks before anything ships

    On every push (GitHub Actions)
    • Server: pyflakes, 109 tests on a real Postgres
    • App: typecheck, lint, tests
    • Known vulnerabilities: pip-audit, npm audit
    Every Monday

    The same checks run again, so a newly published vulnerability fails the build. Dependabot opens update pull requests weekly.

    In production
    • Sentry for errors
    • GET /health checks the database and worker
    • JSON logs with no secrets or message text
    • Daily backups kept 14 days

    How the product changed

    Demo (Oct 2026)
    A single-company demo with project management built in: tasks, schedules, stages, a "My tasks" tab.
    Version 2.0 · 2 Nov
    Becomes a real MVP: Postgres, many companies, sign-in codes, push, files. Tasks move out to the company's PM app; Siteline's bot reads them.
    Version 2.1 · 2 Nov
    The PM app owns the bot's logic. Siteline offers the Cards API and only delivers.
    Version 2.2 · 3 Nov
    Chat only. Projects and channels are just conversations made in Siteline; the PM app's only part is sending cards to people.
    3–4 Nov
    Email-only sign-in, audits, WhatsApp-style bubbles, message search, rate limits, Expo SDK 58.
